## Copy-ready project text

**Title:** RelayLine

**Tagline:** Stay discoverable, even when your service isn't.

**Primary track:** Censorship Resistance. Optional additional tracks: Security and Open Source **only if you deliberately select them**. Do not select Best Indian Use Case without a qualifying team member or Privacy merely because this is a Web3 app.

**What it does / The problem it solves:**

A website outage can also destroy its visitors' trusted way to find a service. RelayLine lets a publisher sign a versioned primary-and-fallback HTTPS recovery manifest on Arkiv Tiramisu. An independent reader queries Arkiv directly, checks the record's immutable on-chain creator against a wallet authenticated out of band, validates revisions and signed control records, and presents authorized recovery destinations without calling the publisher's website or a RelayLine-controlled service-record database. A second wallet's look-alike announcement cannot pass as the pinned publisher. Optional short-lived, signed monitor observations can qualify endpoint health, while root-authorized rotation and revocation let readers fail closed. Real transaction-backed testnet evidence is documented; the prototype does not claim universal censorship resistance, real-world domain ownership, guaranteed fallback uptime, or a production security audit.

**Challenges I ran into:**

The difficult part was deciding which identity is actually trusted: a typed `publisher` attribute is forgeable, while Arkiv's immutable record creator gives a verifiable cryptographic origin that still requires off-chain identity vetting. We also needed deterministic query pagination at a consistent block snapshot, appropriately short observation lifetimes, a two-monitor threshold, and fail-closed control handling when publishers can delete/expire control records. Our evidence report separates real Tiramisu transactions from offline simulations; `arkiv/friction.md` records versions, expected behavior, observed outcomes, and reproduction steps without inventing Arkiv bugs.

**Why Arkiv?**

Without a shared, publicly queryable record layer, users must trust a single provider-controlled API or the very website that went offline. Arkiv provides typed, indexed entities, independent public queries, immutable on-chain creator attribution, and entity expiration aligned with the product's manifest/observation/control lifetimes. Plain Postgres reintroduces a private operator dependency. IPFS alone does not supply the same active typed-query and expiry behavior. Private keys, real-world identity verification, HTTPS probes, and local rollback memory deliberately stay off Arkiv.

**How RelayLine uses Arkiv (source pointers):**

- `src/write.mjs`: explicitly wallet-signed 30-day manifest creation with typed project, service ID, kind and revision attributes.
- `src/query.mjs`, `src/policy.mjs`, `src/control-policy.mjs`: snapshot-aware typed queries, pagination, immutable `$creator` verification, revision/revocation/rotation policy.
- `web/reader.mjs`, `src/browser-arkiv.mjs`: browser-side Arkiv RPC reads with no RelayLine publisher backend.
- `src/monitor-arkiv.mjs`, `src/monitor-policy.mjs`: short-lived signed observations, trusted-witness quorum; expired records correctly become unknown.
- `src/control-arkiv.mjs`: signed revocation and one-hop, root-authorized wallet rotation.
